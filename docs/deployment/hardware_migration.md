# Hardware Migration: Simulator to BluePill (STM32)

## Overview
This document outlines the steps required to move the flight software from the Mac/Linux Simulator to the target **STM32F103 (BluePill)** hardware.

## Step 1: Toolchain Switch
The `CMakeLists.txt` must be updated to use the cross-compiler:
- Change compiler to `arm-none-eabi-gcc`.
- Add MCU-specific flags: `-mcpu=cortex-m3 -mthumb`.

## Step 2: Swap the FreeRTOS Port
The "Plumbing" layer must be swapped:
- Delete `adcs/FreeRTOS/port.c` (POSIX version).
- Restore the `adcs/FreeRTOS/ARM_CM3/` version of `port.c` and `portmacro.h`.

## Step 3: Hardware Abstraction Layer (HAL)
The "Body" must be added:
- Include the STM32 HAL and CMSIS drivers (usually in `Drivers/` and `Core/`).
- Link the Linker Script (`.ld`) and Startup File (`.s`) generated by CubeMX.

## Step 4: The v_bus Abstraction (HAL)
We use a **Hardware Abstraction Layer (HAL)** in `shared/ipc/v_bus.c` to separate mission logic from hardware pins.

- **In Simulation:** `v_bus.c` uses Unix Domain Sockets (`/tmp/v_bus.sock`) to pass CCSDS packets between the OBC and ADCS processes.
- **On Hardware:** You replace the socket code in `v_bus.c` with `HAL_SPI_Transmit` and `HAL_SPI_Receive`.

Because your tasks only call `v_bus_send()`, they don't know (or care) if the data is traveling over a Mac socket or a physical copper wire.

## Step 5: Update Mock Implementations
The "Mocks" in the communication layer must be replaced with real hardware calls:
- **SPI:** Replace `printf` in `spi.c` with `HAL_SPI_Transmit` and `HAL_SPI_Receive`.
- **UART:** Redirect standard output to a physical UART port for telemetry.

## Step 5: Verification
1. Compile using the ARM toolchain.
2. Flash the `.bin` or `.elf` file to the BluePill.
3. Verify the 50Hz heartbeat using an oscilloscope or logic analyzer on a GPIO toggle.
